# A7: Plan gate on every API key use

No migration. Every request authenticated with an API key checks, at request time, that the key's brand is still on a plan with API access.

## What shipped

`assertBrandApiAccess` reads `profiles.role` and `profiles.plan` for the key's brand id with the service-role client. The call is allowed only when `role` is `brand` and the plan is a known `PlanId` whose `PLANS[plan].features.apiAccess` is true. That is the same rule as `brandHasApiAccess`. Operator and the legacy agency plan pass. Free, Starter, an unknown plan, a missing profile, and any other role are denied.

The denial is HTTP 403 `{ "error": "Your plan does not include API access.", "code": "plan_no_api_access" }`. Other auth errors stay `{ "error": "<message>" }` with no `code`. The check runs after the key is tied to a user and before `last_used_at` or the `api_call` event, so a denied call touches neither.

A profiles read error throws a plain Error. The route returns 500. The key and the brand email are not logged.

Tay calls `callTool` in process with `keyId: null`. That path does not call `resolveApiRequest` or this gate, so Tay works on every plan, including Free.

## Access

No new table and no grant change. The read is `profiles` by id through `supabaseAdmin`, selecting `role, plan` only.

## Known gaps

- Key creation is unchanged. A5 still decides who can mint a key.
- The per-key rate limit is unchanged.
- `plans.ts` was not edited. Free and Starter stay without `apiAccess`. Operator and legacy agency stay with it.
- Tay is not plan-gated. CA1 leaves the assistant on every brand plan.
- No migration. Nothing here is applied to the live database.
