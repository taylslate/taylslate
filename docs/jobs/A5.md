# A5: API key settings for brands

No migration. A brand creates, lists, and revokes keys at `/settings/api-keys`. The plaintext secret is returned once from `POST /api/settings/api-keys` and is not stored.

## What shipped

`/settings` gains one brand-only link card, "API keys", directly after Brand profile. Show, agent, and agency roles do not see it. The rest of that page is unchanged, including the disabled Generate API Key control.

`/settings/api-keys` is a server page. No session redirects to `/login?next=/settings/api-keys`. Any role other than `brand` is `notFound`. The brand id is the session user id. Role and plan are read from `profiles` by that id (`role, plan` only).

Creating a key requires `PLANS[plan].features.apiAccess`. Operator and the legacy agency plan have it. Free and Starter do not. A brand without access still sees existing keys, can revoke them, and sees "API keys are part of the Operator plan." with a link to `/settings/billing`. `POST` returns 403 for that case.

`POST` accepts `{ name, scopes }` only. The name is trimmed, 1 to 60 printable characters. Scopes are a non-empty deduped subset of `read`, `write:campaigns`, and `write:outreach`. A brand can hold 10 active keys. The 11th active key is 409: "You have the maximum of 10 active keys. Revoke one first." The response is `{ key, secret }` with `Cache-Control: no-store`. `key` is the allowlist `id, name, prefix, scopes, created_at, last_used_at, revoked_at`.

`GET` returns `{ keys }` using that same allowlist. `DELETE /api/settings/api-keys/[id]` revokes one unrevoked key owned by the session brand. Another brand's id, a bad id, and an already revoked id are 404.

`POST` and `DELETE` require the Origin host to equal the request host. Create is limited to 10 per user per hour (`api_key_create_user_hour`). Revoke is limited to 30 per user per hour (`api_key_revoke_user_hour`). Both fail closed. The JSON body cap is 8 KB.

The browser keeps the secret in component state, in a read-only field, until Done or until the page unmounts. It is not written to a URL, storage, a cookie, or a log.

## Access

No new table and no grant change. Reads and writes go through `createKey`, `listKeys`, and `revokeKey`, which already use the service role and filter by `brand_id`.

## Known gaps

- A7 now enforces apiAccess on every `/api/v1` and MCP use. A downgraded brand's key gets 403 `plan_no_api_access` and does not resolve until the plan includes API access again.
- `/settings/agent-actions` is linked and not built here.
- The disabled Generate API Key button on `/settings` is unchanged.
- Two overlapping revokes can both observe the key as active. A later revoke is 404.
- This job does not apply migration 057. If `api_keys` is missing, the page shows a generic load error and the routes return 500.
