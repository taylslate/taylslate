# S3: shows writes are owner or admin

Migration 066 is written and not applied. Nothing here was run against `ldtmhafewfifdizgfrnn`. Apply it after 065.

## What shipped

`canEditShow(userId, showId)` is true for an internal admin (`INTERNAL_ADMIN_EMAILS`, or `profiles.role` text `admin`), an agent with `agent_show_relationships.status = approved`, and a show user whose `show_profiles.id` is in `getVerifiedProfileTies`. `shows.agent_id` alone is not enough. A pending or rejected link does not grant edit rights. A `podscan_id` is not a tie. A missing show or a failed read is false.

`PATCH /api/shows/[id]` calls `canEditShow` and returns 403 otherwise. The body still drops `id` and `created_at`. It also drops `agent_id`, `is_verified`, `is_claimed`, `podscan_id`, and `is_discoverable` unless `isShowsAdmin` is true. The bare `role === "show"` pass is gone.

`POST /api/shows/[id]/enrich` returns 403 unless `canEditShow`. `POST /api/shows/enrich-batch` skips any show that fails `canEditShow`, records it as `skipped` / `not_permitted`, and enriches the rest. `POST /api/shows` allows an agent or an admin and returns 403 otherwise. A non-admin create forces `is_discoverable` false and sets `agent_id` to the caller. `is_verified`, `is_claimed`, and `podscan_id` from the body are ignored. `POST /api/shows/import` allows `role === "agent"` or an admin, and otherwise returns 403.

`updateShow`, `importShows`, and `updateShowEnrichment` write through `supabaseAdmin`. `importShows` sets `shows.agent_id` to the session user and ignores a body `agent_id`. A non-admin import inserts `is_discoverable` false. An admin import is discoverable unless the row sets it false. The roster link stays pending. `approveRosterLink` in `lib/reps/store.ts` approves a pending roster link. It sets `is_discoverable` true only when `shows.agent_id` equals the link's `agent_id`. Any other show stays hidden. `GET /api/shows/[id]` returns a hidden show to its creating agent (`shows.agent_id`) or an admin. Everyone else still gets 404. `POST /api/shows/[id]/claim` returns 404 for a hidden show unless the caller is that agent or an admin, and the success body omits the show row.

`066_shows_write_policy.sql` drops "Shows insert by authenticated" and "Shows update by authenticated", and revokes insert, update, and delete on `public.shows` from authenticated. Authenticated keeps SELECT. "Shows are publicly readable" stays. Anon is not granted select.

## Session writes to shows

Search: `createClient` from `lib/supabase/server`, then `.from("shows")` followed by `insert`, `update`, `upsert`, or `delete`.

Result: none. The three functions above were the session writers. They now use `supabaseAdmin`.

Reads that still use the session client, all behind a signed-in route or a dashboard page: `getAllShows`, `getShowById`, `getShowsFiltered`, `getShowsByAgent`, `getShowsByIds`, `getDashboardShowCounts`, `getShowsNeedingEnrichment`, the enrich route's load, `POST /api/deals` name lookup, `POST /api/imports/past-campaigns` name hint, and the past-campaigns page.

Already on `supabaseAdmin`, not changed: `createShow`, `backfillShowPodscanData`, `backfillShowMediumFields`, `lib/shows/apply-geography.ts`, `app/api/admin/seed-deal/route.ts`.

`scripts/seed-shows-only.ts`, `scripts/seed-from-podscan.ts`, and the `scripts/backfill-show-*.ts` and `scripts/backfill-purchase-power.ts` files construct a client with `@supabase/supabase-js` and `SUPABASE_SERVICE_ROLE_KEY`. They are not the cookie session client.

Browser code does not write `shows`.

## Known gap

`createShow` without an `actor` option still inserts as service_role for discovery, outreach materialization, show surfaces, and the admin seed routes. Those callers were not changed. After 066, authenticated cannot insert into `shows` through PostgREST.
