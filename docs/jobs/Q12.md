# Q12: Roster dispute block and rep owner heads-up

Migration 081 is in this PR and is not applied. 075 is live and was not edited. Nothing here was run against `ldtmhafewfifdizgfrnn`. No Vercel env or region change. `lib/stripe`, `lib/payouts`, `lib/billing`, and `lib/airchecks` were not edited.

## What shipped

An open row in `roster_link_disputes` blocks approve. `assertNoOpenDispute` runs after the admin check and before the update. A read error fails closed. Migration 081 adds a BEFORE UPDATE OF status trigger that raises P0001 when the new status is approved and an open dispute exists. Reject and updates that do not touch status are unchanged. `approveRosterLink` maps that P0001 to the same dispute error. Nothing is published.

`POST /api/admin/roster-links/[id]` with `{ action: "resolve_dispute", note }` resolves every open dispute on that link. The note is required, trimmed, 1 to 500 characters. `resolved_by` is the session admin. A repeat or a link with no open dispute is 409. A missing `resolution_note` column is 503, "Resolving disputes needs migration 081." Resolve does not approve, reject, publish, or email. Only `isShowsAdmin` can resolve.

The dispute route writes `roster_link.dispute_opened` on the first insert. A unique violation reads the existing row. Open stays "already flagged". Resolved is 200 `{ ok: true, result: "already reviewed" }` with no insert and no email.

`/admin/roster-requests` keeps the pill. A disputed row disables Approve, shows "Approval is blocked while the owner's dispute is open. Resolve it first.", and offers "Resolve dispute for {show}". Success clears the pill in local state, leaves the row pending, and re-enables Approve. Reject stays available. Other rows are unchanged.

`renderRosterRepOwnerHeadsUp` has two variants. Import: "{Show} already has a verified owner". Verified later: "{Show} now has a verified owner", and the link is pending review or approved. Neither names the owner, a dispute, another rep, commission, or exclusivity.

`notifyRepsOfOwnerVerification` claims `roster_owner_verified_notices` first (unique on link and proof). Only the inserter sends, with `recipientProfileId` set to the rep. `sent` stores `sent_at`. `no_api_key` and `managed_inbox_unset` keep the row and are not retried. `send_failed` deletes the claim. A missing table logs one line and sends nothing. Cap 50 links per call. A link whose agent is the proof's user is skipped. Rejected links are skipped.

`notifyRosterImportCommit` calls that helper after the owner notices, for committed `link_existing` and `exclusive_conflict` rows whose proof is verified. A preview, a retry, a `new_show` row, and `POST /api/shows/import` send none.

`sweepOwnerVerificationNotices` finds a verified proof and a pending or approved link on the same show with no notice row, when the proof's `verified_at` or the link's `created_at` is within 7 days. Limit 100. Trigger `verified_later`. Exposed as `GET /api/cron/roster-owner-notices` (daily 21:00 UTC, `CRON_SECRET` bearer) and `POST /api/admin/roster-links/owner-notices` (session, then `isShowsAdmin`).

Audit events, entity `roster_link`. Payloads are ids, counts, and lengths only:

- `roster_link.dispute_opened`
- `roster_link.approve_blocked`
- `roster_link.dispute_resolved`
- `roster_link.owner_heads_up`

## Open questions

Defaults below are what this job built. They are pending Chris's confirmation.

2. Can the disputing owner withdraw their own dispute? Default: no.
3. After a resolve, can the same owner flag again? Default: no. 075's unique key stays, and the reply is "already reviewed".
4. A dispute on an already approved link does not demote or hide the link. Default: no change.
5. Should the admin page show the owner's dispute note? Default: no. It stays in the admin alert email.
6. Heads-up timing. Default: sent at import commit when the show is already owned, and by the 7-day sweep, the daily cron, or the O2/O4 call when the owner verifies later. The import copy says the owner was told. It does not mention a dispute.
7. Preview database. The repo has no `supabase/config.toml`. `000_drop_and_recreate.sql` creates the same tables 001 creates, so a branch that replays the whole folder should fail at 001. Default: a throwaway project, not a branch. See the walkthrough.
8. Out of scope, noted only. The `/shows` "Upload a CSV" button posts to `/api/shows/import` and inserts a new show. It does not link an owned show, so no owner notice, dispute, or heads-up can happen from it. This job does not change that path. 9. "Log in as" covers brand1 and show1 only. The view switch cannot act as the agent. Default: no Test Agent 1 in the founder test login. The walkthrough uses a real email-code sign-in as `chris+agent@taylslate.com`.
