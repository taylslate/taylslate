# R1: Show / Creator sign-up with an email code

Shows and creators can now sign up on their own at `/signup/show` with a 6-digit email code and no password. They get a `show` account, finish the existing show onboarding, and land on the existing prove-ownership page at `/settings/ownership`. They stay unverified until they prove ownership there. Builds on the S-E rate limits, O2 (description-code proof, PR 106), and O4 (admin review queue, PR 107).

## The flow

1. A visitor reaches `/signup/show` from `/signup` ("Are you a show or creator? Sign up with an email code"), from `/login` ("New show or creator? Sign up"), or from the role picker's Show / Creator card (which signs the password session out first).
2. The page posts `{ email, next: "/onboarding/show", intent: "show_signup" }` to `POST /api/auth/login/otp`. An address with no auth user and no outreach token gets a locally minted 6-digit code, stored hashed with the `show_signup` pending marker. An existing user gets a normal login code and keeps their role. The response is `{ ok: true }` either way.
3. `POST /api/auth/login/otp/verify` checks the pending hash and expiry. On the `show_signup` marker it skips the outreach lookup, calls `createShowAccount(email, "show_signup")` (role `show`, tier `free`, both hard-coded), opens the session from an admin magic link's hashed token, and returns `next` (default `/onboarding/show`).
4. The dashboard layout routes a `show` account without an onboarded profile to `/onboarding/show`. After the summary step, `complete()` with no pitch `redirect_to` now pushes `/settings/ownership`, where the existing O2/O4 proof flow runs. The show stays unverified until that finishes.

## Routes and files

- `app/api/auth/login/otp/route.ts`: optional `intent` field; only the exact string `show_signup` means anything. Mints the sign-up code for an unknown address without an outreach token. `Cache-Control: no-store` on every response.
- `app/api/auth/login/otp/verify/route.ts`: the no-user branch handles the `show_signup` marker. `Cache-Control: no-store` on every response.
- `lib/auth/login-otp.ts`: `SHOW_SIGNUP_INTENT` and `SHOW_SIGNUP_PENDING` (both the literal `show_signup`).
- `lib/auth/login-otp-show.ts`: `createShowAccount(email, source = "email_code")`; the source argument only labels `user_metadata.source`.
- `components/auth/show-email-code.tsx`: optional `intent?: "show_signup"` prop, sent in the code request only when set. Existing callers send the same body as before.
- `app/(auth)/signup/show/page.tsx`: the new page. A signed-in visitor is sent to `/dashboard`.
- `app/(auth)/signup/page.tsx`, `app/(auth)/login/page.tsx`: one link each to `/signup/show`.
- `app/onboarding/roles.tsx`, `app/onboarding/page.tsx`: the Show / Creator card (`SHOW_SIGNUP_OPTION`, kept out of `ONBOARDING_ROLES`). Picking it signs out and goes to `/signup/show`; it never calls `/api/onboarding/role`.
- `app/onboarding/show/summary/summary-client.tsx`: the final redirect goes to `/settings/ownership` instead of `/dashboard`; the pitch `redirect_to` behavior is unchanged.
- `proxy.ts`: one line, `/signup/show` added to the public-route allowlist. This file is outside the R1 Owns list, but without it the proxy bounces every signed-out visitor to `/login` and the page is unreachable. Flagged for review.

## The marker

`login_otp_limits.pending_outreach_id` is free `text` with no foreign key (migration 051). The sign-up code stores the literal `show_signup` there; real outreach ids are UUIDs, so the marker cannot collide. The `login_otp_consume` RPC stores and returns it unchanged. No migration.

## Rate limits

- `enforceLoginCodeSend` (per email and per IP, fails closed) runs first, unchanged.
- One new closed rule through `enforceRules` in the send route: bucket `show_signup_ip_day`, keyed by client IP, 10 per day. It runs on every show-signup request, whether or not the address has an account, so timing does not reveal accounts.
- `enforceLoginCodeVerify` and the RPC's 5-wrong-codes lock apply to verification, unchanged.

## Role-escalation guarantees

- The role is never read from the request. A self-signed-up account is always `role: "show"`, `tier: "free"`, hard-coded in `createShowAccount`.
- `role`, `tier`, and unknown `intent` values in any request body are ignored.
- `ALLOWED_ROLES` in `/api/onboarding/role` is untouched (`brand`, `agency`, `agent`); `show`, `show_signup`, and `admin` are rejected, and a `show` account posting `brand` gets 403.
- An existing auth user who uses show sign-up gets a normal login code, keeps their role, and no `profiles` write happens.
- The send route answers `{ ok: true }` on success paths whether or not the address has an account, and no response carries DB or Supabase error text.

## Known gaps

- `proxy.ts` was touched outside the Owns list (one allowlist line, see above). If that is wrong, the revert is one line, but the page then needs another way to be publicly reachable.
- `/signup/show` metadata is set in R1-FIX (`docs/jobs/R1-FIX.md`): a `PUBLIC_PAGES` entry and `app/(auth)/signup/show/layout.tsx`.
- No captcha on `/signup/show`. The send route's per-email, per-IP, and per-day limits are the only brake on sign-up attempts, by design (no server-side captcha secret in this job).
- An existing user who lands on `/signup/show` sees "We emailed you a 6-digit code" and signs in to their existing account with their existing role; there is no copy telling them they already had an account (deliberate: no account-existence leak).
- The summary button copy is updated in R1-FIX (`docs/jobs/R1-FIX.md`) to "Next: prove you own the show". It still goes to `/settings/ownership`.
- The verify response's `next` for a show sign-up with a tampered `next` falls back to `/dashboard` (via `safeLoginNext`), not `/onboarding/show`; the dashboard layout still routes the show to onboarding, so the flow self-heals.
