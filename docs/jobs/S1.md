# S1: public table grant hardening

Migration 060 is applied on `ldtmhafewfifdizgfrnn` (PR 40). The first paste left anon `SELECT` on `public.shows`. That grant line has been removed from the file, so pasting 060 again does not put it back. S2, migration 065, revokes it on a database that still has the old grant. The rest of this note is the record of the first apply.



## What shipped

`supabase/migrations/060_public_grant_hardening.sql` revokes excess table privileges on the 26 public tables from the 2026-10-25 read-only audit. RLS was already on for all 26. The migration enables it again so a rebuild stays locked. No policy, function, or table shape changes. `service_role` is not granted or revoked.

Anon keeps one privilege: `SELECT` on `public.shows`. `GET /api/shows` and `GET /api/shows/[id]` read that table with the anon key when there is no session. The policy "Shows are publicly readable" is unchanged.

On the other 25 tables, anon and public lose every privilege. On shows, anon loses `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER`. Authenticated loses `TRUNCATE`, `REFERENCES`, and `TRIGGER` on all 26, and keeps `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on the other 22.

`api_cache_log`, `domain_events`, `event_log`, and `show_claims` are service_role only. No policies were added. A grep of session code (`createClient` from `lib/supabase/server`) found no reads or writes of those three log tables. The writers use `supabaseAdmin`. Nothing in the app reads `show_claims`. `show_claims` has no rows and is dropped in O1 (061). This migration only locks it.

## Throwaway grants after

They exist on the live project. The test then granted all seven privileges to anon, authenticated, public, and service_role on the 26 tables, matching the live audit, and applied 060.

Anon and authenticated `SELECT` on `shows` succeed. Authenticated `SELECT` on the four service_role tables fails. Applying 060 a second time succeeds and leaves the same anon grant.

## Follow-ups not fixed here

- `shows` policies "Shows insert by authenticated" and "Shows update by authenticated" only check `auth.uid() IS NOT NULL`, so any signed-in user can insert or update any show through PostgREST. The fix needs `updateShow`, `importShows`, and `updateShowEnrichment` moved to `supabaseAdmin` first. Those three still use the signed-in server client.
- Anon `SELECT` on `shows` is table-level, so the signed-out catalog read returns every column, including contact email and rate fields. There is no notes column on `shows`. The follow-up is an explicit column list on the two public routes through `supabaseAdmin`, or a column-level anon grant. See the S1 known gaps in `docs/SENIOR_DEV_HANDOFF.md`.
- `show_claims` is dropped in O1.
