# S2: show data is login-only

Migrations 065 and 066 are written and not applied. Nothing here was run against `ldtmhafewfifdizgfrnn`. 060 is already applied. Do not re-run 060 after 065. 061 is reserved for the O1 drop of `show_claims`. 062, 063, and 064 are not in the repo.

The column allowlist in the original S2 note is not what shipped. The app is login-only. Signed-out callers do not receive show rows.

## What shipped

`GET /api/shows` and `GET /api/shows/[id]` return 401 when no user is signed in. They still return the full row to a signed-in caller, including contact, rate card, sponsors, slots, and income demographics. `/shows` and the other dashboard pages are not on the proxy allowlist, so a signed-out visit redirects to `/login?next=`.

There is no MCP auth. v1 bearer keys (`ts_live_<prefix>_<secret>`, `api_keys.brand_id`) are the agent path. `resolveApiRequest` rejects a key whose `brand_id` is not a `profiles.id`, with 401 and no `last_used_at` update. `GET /api/v1/shows` and `GET /api/v1/shows/[id]` already required a key with read scope. The show serializer now includes `contact` (`name`, `email`, `method`) plus the existing rates, sponsors, slots, and income demographics. A signed-out caller has no key and gets 401.

`065_shows_login_only.sql` revokes every anon and public privilege on `public.shows` and on every table in `public`. It sets default privileges so new tables, sequences, and functions in `public` grant nothing to anon or to public, for the pasting role and for `postgres` and `supabase_admin` when that role exists. Existing function execute grants are not swept.

## Routes

Newly rejected for a signed-out caller:

- `GET /api/shows` returns 401.
- `GET /api/shows/[id]` returns 401.
- `/shows` redirects to `/login?next=%2Fshows` (proxy, already true for dashboard pages).

Already required a session, and still do: `GET /api/crm/shows`, `GET /api/crm/shows/[showId]/contacts`, `GET /api/crm/shows/[showId]/notes`, `GET /api/crm/shows/[showId]/deals`, `GET /api/reps/shows/[showId]`, `GET /api/show-profile`, `GET /api/show-surfaces`, `GET` and `POST /api/deals` (show name lookup), `POST /api/imports/past-campaigns` (show name hint), `GET /api/admin/shows/[showId]/annotations`, `POST /api/shows/[id]/claim`, `POST /api/shows`, `PATCH /api/shows/[id]`, `POST /api/shows/[id]/enrich`, `POST /api/shows/enrich-batch`, `POST /api/shows/import`.

Already required a v1 key, and now also a profile row: `GET /api/v1/shows`, `GET /api/v1/shows/[id]`, and the other `withApiRead` routes (`/api/v1/campaigns`, `/api/v1/deals`).

`/outreach/[token]` stays public. It is a token-gated pitch, not a catalog read.
