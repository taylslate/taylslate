## What shipped

`071_shows_select_policy.sql` drops "Shows are publicly readable" and creates "Shows readable by signed-in participants" `FOR SELECT TO authenticated`. A signed-in caller sees a `shows` row when any of these hold:

- `is_discoverable` is true
- `shows.agent_id` is the caller
- an `agent_show_relationships` row for that show is `approved` and belongs to the caller
- a `deals` row on that show has the caller in `brand_id`, `agency_id`, or `agent_id`
- a verified tie: a deal whose `show_profile_id` is the caller's `show_profiles` row, or a `show_owner` row whose `contact_email` matches the caller's `profiles.email` and the caller has a `show_profiles` row

`show_profiles.podscan_id` is not a tie. Every `auth.uid()` call is `(select auth.uid())`.

Policies on `agent_show_relationships`, `deals`, `show_profiles`, and `profiles` do not read `shows` (confirmed on the live database and in migrations 001, 009, 013, and 055). The branches stay inline. There is no security definer function.

New index, only where it was missing: `idx_agent_shows_show_agent_approved` on `agent_show_relationships (show_id, agent_id) WHERE status = 'approved'`. `idx_show_profiles_user` is created if that name is absent. Live already has it, from migration 009, plus the unique index on `show_profiles.user_id`. `idx_shows_agent`, `idx_deals_show`, and `idx_agent_shows_show` already exist and are left alone.

Grants are re-asserted. Anon and public have nothing on `shows`. Authenticated keeps `SELECT` and loses insert, update, delete, truncate, references, and trigger again. `service_role` is not granted or revoked. The 066 write policies are not changed here. 066 already dropped them.

`EXPLAIN` for `select id from shows where id = <agent A's hidden show>` as Brand B, after `analyze` and 400 extra discoverable rows:

```
Index Scan using shows_pkey on shows
  Index Cond: (id = '<hidden>'::uuid)
  Filter: (is_discoverable OR (agent_id = $0) OR (hashed SubPlan 5) OR (SubPlan 13) OR (hashed SubPlan 33) OR (('show_owner'::text = ANY (data_sources)) AND (contact_email IS NOT NULL) AND (hashed SubPlan 37)))
  InitPlan 1 (returns $0)
    ->  Result
  SubPlan 5
    ->  Seq Scan on agent_show_relationships a
          Filter: ((agent_id = $4) AND (status = 'approved'::text))
  SubPlan 13
    ->  Index Scan using idx_deals_show on deals d
          Index Cond: (show_id = shows.id)
  SubPlan 33
    ->  Nested Loop
          ->  Index Scan using idx_show_profiles_user on show_profiles sp_2
                Index Cond: (user_id = $28)
          ->  Index Scan using idx_deals_show_profile on deals d_1
                Index Cond: (show_profile_id = sp_2.id)
  SubPlan 37
    ->  Nested Loop
          ->  Index Scan using profiles_pkey on profiles p
                Index Cond: (id = $37)
          ->  Index Only Scan using idx_show_profiles_user on show_profiles owner_profile
                Index Cond: (user_id = $37)
```

The lookup uses `shows_pkey`. The deal branch uses `idx_deals_show`. The tie branches use `idx_show_profiles_user` and `profiles_pkey`. At this row count the approved-roster branch hashes the caller's approved show ids (a seq scan of that small set). `idx_agent_shows_show_agent_approved` is present for the show-id-leading probe. A direct equality on `(agent_id, show_id)` uses the existing unique index `agent_show_relationships_agent_id_show_id_key`.
